# Spell System

How spells are stored and customised in VMaNGOS. Spell *templates* come from the client's
`Spell.dbc`; the world database's `spell_*` tables layer server-side behaviour on top of them.
This page maps out which table does what.

---

## The Core: [`spell_template`](world/spell_template.md)

The [`spell_template`](world/spell_template.md) table mirrors and extends `Spell.dbc` for every
spell the server can cast: costs, cast times, cooldowns, effects (1-3), targets, visuals and
text ids. Most content work only touches DBC data; [`spell_template`](world/spell_template.md) matters when you need to
change behaviour without touching the client.

---

## Behaviour Layers

| Table | Purpose |
| :--- | :--- |
| [`spell_proc_event`](world/spell_proc_event.md) | Defines *when* a proc-style spell triggers (on hit, on crit, on being hit, with which cooldown/family mask). |
| [`spell_chain`](world/spell_chain.md) | Spell rank chains: `spell_id`/`prev_spell`/`first_spell` relations and ranks (next rank derived from these). Drives "learn next rank" logic and downranking. |
| [`spell_learn_spell`](world/spell_learn_spell.md) | Spells that auto-teach other spells when learned. |
| [`spell_pet_auras`](world/spell_pet_auras.md) | Auras applied to the caster's pet when a spell is active. |
| [`spell_elixir`](world/spell_elixir.md) | Classifies elixir auras via a mask as Battle/Guardian (both bits = flask) so the "one of each" rules work. |
| [`spell_group`](world/spell_group.md) + [`spell_group_stack_rules`](world/spell_group_stack_rules.md) | Groups auras and defines stacking behaviour between members. |
| [`spell_threat`](world/spell_threat.md) | Threat generated by casting a spell. |
| [`spell_cone`](world/spell_cone.md) | Cone width for cone-shaped target effects. |
| [`spell_target_position`](world/spell_target_position.md) | Explicit destination coordinates for teleport/summon effects. |
| [`spell_script_target`](world/spell_script_target.md) | Hard target requirements for scripted effect targets (specific creature/GO entries). |
| [`spell_check`](world/spell_check.md) | Expected spell properties used by the `.debug spellcheck` command to validate spells against in-code assumptions. |

## Casting Pipeline (simplified)

1. Player/NPC casts → `Spell::prepare` → checks (range, cooldowns, costs, reagents,
   [conditions](world/conditions.md) where applicable).
2. Effect execution resolves implicit targets; [`spell_target_position`](world/spell_target_position.md) /
   [`spell_script_target`](world/spell_script_target.md) override where defined; cones use [`spell_cone`](world/spell_cone.md).
3. Aura application consults [`spell_group_stack_rules`](world/spell_group_stack_rules.md), [`spell_elixir`](world/spell_elixir.md) and
   [`spell_pet_auras`](world/spell_pet_auras.md).
4. Procs roll through rules in [`spell_proc_event`](world/spell_proc_event.md); threat is added via [`spell_threat`](world/spell_threat.md).

---

## Scripted Spells

- **DB scripts**: [`spell_scripts`](world/spell_scripts.md) run the
  [generic script command set](DB-Script-Tables.md) on spell events.
- **C++ scripts**: [`spell_template`](world/spell_template.md).script_name binds to handlers registered in
  `src/scripts/spells` for behaviour too complex for tables.
